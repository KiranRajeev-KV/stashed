# Frontend styling

- Do not add frontend tests or test scripts unless explicitly requested. Use builds, lint, bundle inspection, and manual verification for frontend changes.

- Use Tailwind utilities for component styling, including responsive layouts, pseudo-elements, interactive states, and reduced-motion variants.
- Keep reusable utility strings in the relevant `styles/*-styles.ts` module or colocate small, one-off strings with their component. Keep complete utility names statically discoverable; do not construct utility names dynamically.
- Define shared design tokens in `index.css` using Tailwind's `@theme` API. Put theme-dependent values in the light/dark token sets. Prefer semantic colors, typography, radii, control heights, and breakpoints over repeated literals.
- Typography must use named Tailwind tokens, not arbitrary text/font/leading/tracking values. Use caption for helper text, metadata for tags and dates, ui for controls, and idea-title for both reader and editor titles. Display tokens own their line height and tracking; avoid overriding these per page. Keep micro text for decorative labels, not essential instructions.
- Normal CSS is reserved for theme definitions, document-wide base rules, animation keyframes, and third-party integration that cannot be styled through class names. Explain any new exception with a comment. Do not recreate component stylesheets with `@apply`.
- Maintain the muted Linear-inspired hierarchy: quiet navigation, subtle borders, consistent controls, and prominent content. Single-choice menus use row highlighting, not checkmarks; multi-choice menus may use checkmarks.
- Use `Button` from `components/ui/button.tsx` for actions and `buttonStyles` for action links. Prefer one primary action per action group; use secondary for supporting actions, ghost for low-emphasis actions, and destructive for confirmed destructive actions. Use `loading` and a meaningful `loadingLabel` for pending mutations. Keep menu items, breadcrumb links, and editor toggles specialized.
- Use `ActionFeedback` next to local actions for pending, saved, and failure messages. Keep its live regions mounted. Do not duplicate inline failures in toasts. Reserve success toasts for actions that navigate away, and explain preserved/restored data and the recovery action when a request fails.
- Preserve keyboard focus, disabled states, touch targets, responsive layouts, and reduced-motion behavior. Run `pnpm run knip:all`, `pnpm run build`, and `pnpm run lint` after a styling migration. Visually verify in light/dark and desktop/mobile when a browser is available; disclose when it is not.
- Keep responsive containers shrinkable (`min-w-0`, `minmax(0,1fr)`), wrap long tags and action groups, and constrain popups to the viewport. Reader/editor sidebars stack below `lg`; editor page actions are non-sticky below `lg` to leave space for the keyboard. Formatting controls wrap in source order rather than hiding tools offscreen. Keep horizontal scrolling local to code blocks, not the page.
